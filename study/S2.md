# S2 — Tiles, Spatial Indexes and H3

## The XYZ tile scheme
Web maps cut the Web Mercator world into 256×256-pixel squares. At zoom *z* there are 2^z × 2^z tiles. Zoom 0 is one tile showing the whole world, and each level splits every tile into four children. A tile is addressed as `/{z}/{x}/{y}`, with x counted from 180°W and y from the **top** (north). TMS numbers y from the bottom, so a vertically "mirrored" map usually means XYZ/TMS confusion. Ground resolution is 156 543.03 × cos(lat) / 2^z metres per pixel. At Kochi that is about 150 m/px at z10, **4.7 m/px at z15** and about 1.2 m/px at z17, so our three wards fit on a handful of z15 tiles.

```
 z=0   +-------+        z=1   +---+---+        z=2  16 tiles ...  z=15: 32768 x 32768
       | world |              |0,0|1,0|
       |  0,0  |              +---+---+        Kochi centre (10.008N, 76.302E)
       +-------+              |0,1|1,1|          z10 -> tile x=729,   y=483
                              +---+---+          z15 -> tile x=23329, y=15468
         4^z tiles per level; each child = 1/4 of parent; y grows southward
```

## Raster vs vector tiles
**Raster tiles** are pre-rendered PNG/JPEG images. They are simple and identical everywhere, but the style is baked in, and a new colour scheme means re-rendering. **Vector tiles (MVT)** are Protocol Buffer files that hold the geometry, clipped and quantised to a 4096-unit tile grid, plus attributes. The browser styles them, so one tile set can serve many styles and features stay clickable. PostGIS builds them with `ST_AsMVTGeom` + `ST_AsMVT`, and `pg_tileserv` serves any table this way automatically. **PMTiles** packs a whole tile pyramid into one file. The client pulls individual tiles with HTTP range requests, so static hosting (object storage, GitHub Pages) replaces a tile server.

## GiST indexes and bounding-box pre-filtering
A GiST index on a geometry column is an R-tree over each feature's bounding box. A spatial query runs in two steps. First, a cheap **index scan** using the `&&` (boxes overlap) operator throws away almost everything. Then the exact and expensive geometry test (`ST_Intersects`, `ST_DWithin`, `ST_Contains`) runs only on the survivors. Functions like `ST_DWithin` add the `&&` step themselves, which is why `ST_DWithin(geog, point, 1200)` is fast and `ST_Distance(...) < 1200` is not, since it cannot use the index. Run `EXPLAIN ANALYZE` to confirm you get an "Index Scan using ... gist" rather than a "Seq Scan".

## H3 hexagons
H3 (from Uber) covers the globe with hexagons at 16 resolutions (0–15), plus 12 unavoidable pentagons per resolution. Each step down divides a cell into about 7 children (aperture 7), though children do not nest perfectly inside their parent. Hexagons are useful because all six neighbours share an edge and sit at the same centre-to-centre distance, which suits accessibility surfaces and equal-unit aggregation. Average cell areas: res 7 ≈ 5.16 km², **res 8 ≈ 0.74 km²**, **res 9 ≈ 0.105 km²**, res 10 ≈ 0.015 km². For three Kochi wards, res 9 gives a few dozen cells of roughly city-block scale, and res 8 is about one cell per neighbourhood.
